# Application Interface

This document details the interaction between the React frontend and the FastAPI backend, focusing on the API design and real-time communication mechanisms.

## REST API Integration

The FastAPI backend exposes several core endpoints designed to handle specific domains of the application. The frontend communicates with these endpoints using standard HTTP requests (e.g., `fetch`).

### Core Endpoints

1. **Text-to-Speech Generation (`POST /api/tts`)**
   - **Purpose**: Initiates the conversion of text into speech.
   - **Mechanism**: The frontend sends a JSON payload containing the `message` (text) and the requested `voice`. This endpoint is unique because it responds with a **Server-Sent Events (SSE)** stream rather than a standard JSON response.
   - **Authentication**: When running in `API_ONLY=true` mode, this endpoint requires `x-client-id` and `x-client-secret` headers.

2. **Custom Voice Blending (`POST /api/blend`)**
   - **Purpose**: Allows users to blend two existing voice embeddings to generate a new custom voice embedding.
   - **Mechanism**: Accepts a JSON payload containing admin credentials, a new `voice_name`, the `voice_a` and `voice_b` names, and the blend `ratio`. The backend processes the blend request and saves the metadata locally.

3. **Analytics Retrieval (`POST /api/analytics`)**
   - **Purpose**: Fetches usage statistics for the admin dashboard.
   - **Mechanism**: Accepts admin credentials in the JSON body and returns aggregated metrics (e.g., total files, words processed, average TTFB) queried from the SQLite database.

## Real-Time Streaming with Server-Sent Events (SSE)

Due to the nature of text-to-speech generation, it is beneficial to start playing the audio as soon as the first sentence is processed, rather than waiting for a long paragraph to finish completely. Kokoro TTS achieves this using Server-Sent Events.

### How SSE Works in Kokoro TTS

1. **Connection Establishment**: The frontend makes a POST request to `/api/tts` but keeps the connection open to receive a stream of text data.
2. **Event Types**: The backend emits different status events as it processes the request:
   - `{"status":"thinking"}`: Acknowledges the request and indicates the engine is loading or preparing.
   - `{"status":"text","text":"..."}`: Indicates the specific chunk or sentence currently being processed.
   - `{"status":"audio","text":"...","audioUrl":"/api/audio/chunk-xxxx.wav"}`: Signals that an audio chunk has been successfully generated and saved to the temporary directory. It provides the URL where the frontend can download the actual `.wav` file.
   - `{"status":"done"}`: Signals the end of the stream, prompting the frontend to close the connection.

### Frontend Audio Playback

As the frontend receives `audio` events via SSE, it queues the provided `audioUrl`s. It fetches these `.wav` files sequentially and plays them back-to-back, creating a seamless listening experience for the user even as backend generation continues asynchronously.
