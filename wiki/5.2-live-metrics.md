# Live RAM Metrics

The application provides a dedicated page for real-time memory profiling of the active Text-to-Speech (TTS) session. This feature is crucial for monitoring the resource consumption of the `kokoro-onnx` generation engine and identifying potential performance bottlenecks during audio synthesis.

## Data Source

The Live Metrics dashboard (`LiveMetrics.tsx`) visualizes data embedded directly within the chat session's state. It relies on the `ramMetrics` property attached to assistant messages.

When the backend generates audio, it streams chunks back to the frontend. During this process, the Server-Sent Events (SSE) payload for the `status: 'audio'` event includes a `ramUsageMb` field, which is generated using `psutil` in the backend. This metric represents the RAM consumption for each specific audio chunk generated.

The frontend aggregates these chunk-level metrics into the `Message` object:
```typescript
type Message = {
  // ... other fields
  ramMetrics?: { chunk: string; ramUsageMb: number }[];
  totalWords?: number;
};
```

*Note:* This data is transient and tied to the active session. If the user navigates away or refreshes the page entirely, the session state (and thus the live metrics data) is reset unless persisted by higher-level state management (like in `App.tsx`).

## Dashboard Visualization

The dashboard uses the **Recharts** library to provide two levels of insight:

1. **Session Overview (Average RAM per Message):**
   When the dashboard first loads, it displays a `BarChart`. This chart aggregates the `ramMetrics` for all generated assistant messages in the active session, calculating and displaying the **Average RAM Usage** (in MB) per message. It provides a quick look at the memory footprint of different prompts.

2. **Detailed Analysis (Chunk-Level RAM):**
   By clicking on a specific bar in the overview chart, users can drill down into a specific message. This view renders a `LineChart` showing the sequential RAM usage for each chunk generated within that message. This detailed view is essential for tracking memory allocation fluctuations over the duration of a single generation request.
