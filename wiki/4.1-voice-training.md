# Voice Training

Kokoro TTS supports the addition of custom voices, allowing users to synthesize speech that mimics specific tonal qualities or accents based on an uploaded audio sample.

## The Training Process

While a true deep-learning training process requires substantial GPU compute and time, this application simulates a fast "embedding extraction" or "training" process suitable for edge deployment.

### 1. Uploading the Sample
An administrator uses the frontend UI or directly hits the `/api/train` endpoint via POST. The request must be a `multipart/form-data` payload containing:
- Admin credentials (for authorization).
- `voiceName`: A unique string identifier for the new voice.
- `sample`: A `.wav` audio file featuring clear speech from the target voice.

### 2. Processing and Storage
When the backend receives the request, it performs the following:
- **File System**: The `.wav` file is moved from the temporary upload directory to the persistent storage volume located at `./data/models/`. The application uses `fs.copyFile` followed by `fs.unlink` rather than `fs.rename` to prevent cross-device link errors (EXDEV) common in Docker volume setups.
- **Database Tracking**: A new record is inserted into the SQLite `voices` table, saving the `voice_name` and the specific `file_path`.

### 3. Usage During Synthesis
When a subsequent request is made to `/api/tts` specifying the newly created `voiceName`, the system looks up the database record.

*Note on current limitations*: While the application tracks and saves these custom voice files, natively loading dynamic custom ONNX embeddings at runtime without modifying the underlying `kokoro-onnx` library is complex. In instances where a custom embedding cannot be dynamically loaded by the engine, the application gracefully falls back to simulating the requested voice using a default internal voice (like `af_heart`) to ensure the generation pipeline does not fail.
